# strata-sim

Discrete-event simulation kernel, method dispatch, scopes and stubs, snapshots, the run tree, chaos and metrics.

- Runs in: Web Worker, `worker_threads`
- Specification: spec §11, §12
- Built in: M04 (tasks 0401–0417) (see `plan/ROADMAP.md`)
- Entry point: `src/index.js`, the only file other packages may import (eng §4)

So far, the kernel (task 0401), the worker's host and sandbox (task 0402), method dispatch and `ctx` (task 0403), typed state at run time (task 0404), edges and routing (task 0405), composites (task 0406), base behaviours (task 0407), servers and the self-test helpers (task 0409), scopes and stubs (task 0412), snapshots and time travel (task 0413), run controls (task 0414), run-only edits and branches (task 0415), observing and inspecting for the debugger (task 0416), run sessions in the worker (task 0417) and the walking skeleton (task 0009):

- `Kernel` and `EventQueue`: integer-microsecond simulated time, with events ordered by `(timeUs, priority, seq)` (eng §13). Simultaneous events run in the order they were scheduled. The queue pools its entries: the entry `pop` returns is the caller's until the next `pop`, which takes it back for a later `push`, so a run allocates no queue entries once the queue has reached its depth.
- `createStreams(seed)`: one xoshiro128** stream per component, seeded through splitmix32 from the seed and a hash of the component id, so adding a component never changes another component's stream.
- `log(x)` and `exp(x)`: ports of fdlibm's e_log.c and e_exp.c (as V8 carries them, with its exact `exp(1)`), made of IEEE 754 arithmetic alone, so they return the same bits in every engine. They are for distribution sampling, which `ctx.sample` brings in task 0403, in place of `Math.log` and `Math.exp`, which may differ in the last bit between engines (eng §13). `test/fixtures/log-exp-vectors.json` holds the reference vectors.
- `tools/bench/kernel.bench.js` measures simple events per second in Chromium against the 200,000 of eng §15.
- `createRun({ seed, nodes, edges, record, inspect, snapshotEvery, snapshotBytes })` (`src/run.js`): a run of components with the real `ctx` (spec §8), over the kernel. `run.inject({ node, port, method, body, atUs })` sends a request from outside the run and returns a reply that fills in when the response leaves; `await run.runToEnd()` handles every event, or, with `{ untilUs }`, those due by then, moving the clock there and leaving later ones for the next call; `run.spans`, `run.metrics` and `run.logs` hold the trace and what methods recorded. With `record: true`, `run.recordings` keeps, by edge, each message that reached a component over it, with its method, path, headers, body and arrival time, and each request's response and when it left (task 0412).
  - **Dispatch.** A message runs only a public method that its port exposes (`msg.method`, or the port's default); anything else, a private method included, fails with `E_METHOD_NOT_EXPOSED` and shows as an error span. A method's declared latency, a distribution or the property that holds one, delays its response.
  - **Private calls.** `ctx.call(name, args)` runs the private method now, inside the caller's processing, adds its declared latency to the caller's time, and is a child span.
  - **ctx promises.** `ctx.send(port, method, args)` returns a promise that only the response's arrival, a kernel event, settles; a failed response rejects it with a `CallError` that carries the callee's code, whether Strata's or the component's own. `ctx.emit` sends without waiting. After an event that settles a promise or starts an async method, the run lets microtasks run until eight turns pass with no progress, so a method resumes at the event's simulated time while other messages keep being processed. A call left waiting on anything else fails with `E_BEHAVIOUR_AWAIT`.
  - **init.** A behaviour's `init(ctx)` hook runs once, at the start of the run, as an `init` span, before any message.
  - **The rest of ctx.** `props` (the node's values over the manifest's defaults), `state`, `now` in ms, `random()` and `sample(dist)` from the node's own stream, `fail(code, details)`, `schedule(delayMs, name, data)` for `onTimer`, with a copy of `data`, `await spend(dist)`, which waits that many ms, or a draw from the node's latency stream, in simulated time and keeps the call's server (ADR 0021), `targets(port)`, the edges leaving a port in the order the run was given them, as `{ edge, node, weight }` (ADR 0022), `metric(name, value)` and `log(level, ...args)`.
  - **Edges** (spec §11 "Routing and resources", ADR 0019). A run's edge is `{ id, from, to, method, props }`, with its connection's properties in canonical units; one it lacks costs nothing. Each crossing takes the edge's `latency` (ms, or a distribution sampled from the edge's own stream) plus the transmission delay, size ÷ `bandwidth`, and is lost with probability `packetLoss`. A message's size is the `sizeBytes` it was sent with, or the edge's `payloadSize`, which responses use too. A request with no response within `timeout` is sent again after `retryBackoff`, doubling each time and moved by up to `retryJitter` of itself either way, until `retries` run out and `ctx.send` rejects with `E_SIM_TIMEOUT`. Each attempt is a `send` span (with `edge` and `attempt`) under the caller's span, and a late response to an attempt that timed out is ignored.
  - **Routing** (`src/route.js`). `ctx.send(port, method, args, { path, headers, sizeBytes })`, and `ctx.emit` likewise, give a message its protocol details. The edges leaving the port whose rules all hold may carry it: `method a, b`, `path /orders` (a prefix, by whole segments), `header name = value` (names in any case), `when <expression>`, and the edge's `method`. Edges with conditions beat edges with none, and a draw weighted by `weight n` (1 by default), from the port's own stream, picks among several. With none left, the send fails with `E_SIM_NO_ROUTE`; a malformed rule fails `createRun` with `E_SIM_ROUTE_INVALID`. A send that names an `edge` goes over it and skips the rules, and one that does not leave the port fails with `E_SIM_EDGE_NOT_FOUND` (ADR 0022).
  - **Expressions** (`src/expr.js`). `compile(text, names)` turns a `when` expression into a function without eval: literals, names, `.` and `[…]`, `== != === !== < <= > >=`, `&& || !`, unary minus and parentheses. `==` does not convert types, orderings compare numbers with numbers and text with text, and member access reads only a value's own data.
  - **Messages.** A method gets `msg` with `kind`, `method`, `path`, `headers`, `body`, `sizeBytes`, `attempt`, `traceId`, `spanId` and `parentSpanId`, and nothing of the run's own. `run.inject` takes `path`, `headers` and `sizeBytes` too.
  - **Composites** (spec §6 "Black box or expanded", §7). A run's node may be a composite, `{ composite: { mode, bindings, exits, contract } }`. Expanded, a message to it goes on, with no span of its own, to the component its binding names one level down (`E_METHOD_UNBOUND` when it has none), and a message from the inner port behind one of its out ports leaves through that port. As a black box, its own behaviour answers, or, without one, its contract: an empty answer after the service time the contract bounds (`serviceTime` or one of its statistics).
  - **Base behaviours** (`src/base.js`, spec §8, §9). A component that extends a base type (the first in its `lineage`, or its `extends`) simulates without code. `base:service` answers every endpoint after `serviceTime`, and `health` with `{ status: 'up' }`, on `instances × concurrency` servers. `base:queue` keeps messages up to `capacityMessages` (`QUEUE_FULL`), in flight until `ack` or `nack` (`UNKNOWN_MESSAGE`). `base:topic` keeps a log that each consumer group polls from its own offset. `base:store` keeps items by key, reading in `readLatency` and writing in `writeLatency` (or `latency`). `base:cache` keeps entries, in `hitLatency`. `base:proxy` forwards on `out` with the message's path and headers and no method, so the edge's method is called (ADR 0019's amendment), in `processingLatency`. `base:timer` emits on `out` when triggered, unless paused (`PAUSED`). `base:external` answers after `latency`, failing at `errorRate` (`UNAVAILABLE`). `base:client` answers nothing. The base's state fields go under the manifest's, its methods under the entry's, and its latency properties apply where the manifest gives a method none. The starter components complete them in 0408 to 0411.
  - **Servers** (ADR 0020, spec §11 "Routing and resources"). A node whose manifest or base behaviour has `servers` admits each public call to a free server, and the rest wait first in, first out. `count` multiplies its entries (properties, `state.<field>` or numbers), and a node lacking one has no limit. A call waits at most `timeout` ms (`TIMEOUT`), and a full `backlog` refuses it (`BACKLOG_FULL`). A call keeps its server until its response leaves; its span starts when it arrives and records `queuedUs`. A count that grows from state admits waiting calls when a server is released or when any call or timer of the node ends. The run records the gauges `backlog` and `utilisation` for nodes with a limit; `servers.metrics` renames the waiting gauge and adds the busy count, such as `{ busy: 'activeConnections', waiting: 'waitingConnections' }`.
  - **State** (`src/state.js`, spec §6). A node's state starts from the manifest's initial values, then its fixtures (a table's rows from CSV, `fixtures: { orders: { csv } }`), then its instance overrides (`state`), each checked against the field's schema. Methods see it through a view that checks every write against the part it writes: a queue's or list's items, a map's values, a table's rows (every column and no other, unique keys) and cells, and a whole field. In development builds the view refuses fields the manifest does not declare (`E_BEHAVIOUR_UNDECLARED_STATE`). Every change is recorded in `run.changes` with its event number, span, node, path and value, for the debugger. Message bodies and responses are copies, so no other node reaches a node's state.
- `createControl(input, { scheduler, durationMs, frameMs, speed })` (`src/control.js`, spec §12, task 0414): a run with its controls. `control.state` moves through the states of spec §12's diagram, `ready`, `playing`, `paused`, `finished` and `stopped`, and any other move fails with `E_RUN_STATE`. `play()` advances simulated time on each frame of the injected scheduler (`frameMs`, 16 ms), by the frame's length times the speed; `setSpeed(0.1…Infinity)` changes only how fast. `pause()` stops at the next event boundary and `await idle()` waits for the frame being played. `stop()` keeps the run to inspect, and `restart()` starts a fresh one from time zero with the same input and the requests `inject` gave before it started. `runToEnd()` runs at full speed to the end, `durationMs` (60 s by default) or no event left, or until a breakpoint; `setBreakpoint({ node, method })` pauses before a message arrives at a component, and `setBreakpoint({ when })` before the event in which a happening `when` holds for happens (strata-debug's breakpoints, task 0416); the next move goes past it. `following` is the followed trace. `step(n, unit)` and `seek(target)` pause after. `follow(trace)` sets the frame, the followed request's latest running call; `stepInto()` runs to the next private call, or call on a component deeper inside an expanded composite, within it, and `stepOut()` runs the frame's call to its end and moves to the call that made it.
  - **Run-only edits and branches** (spec §12 "Editing a paused run", "Run tree", task 0415). While paused, `control.edit(edit)` takes a run-only edit: `{ kind: 'props', node, props }`, `{ kind: 'state', node, path, value }`, `{ kind: 'code', node, behaviour }` or `{ kind: 'structure', add: { nodes, edges }, remove: { nodes, edges } }`. `continuations()` says how the run may go on: `resume()` for property and state edits only, from now on; `replayFromHere()`, a branch run that shares this one's history and plays on with the edits, unless a component the edits remove has work on its way; and `restartWithChanges()`, a fresh run from time zero with every edit so far. Any other fails with `E_RUN_EDIT`. `control.runs` is the run tree, each with its `parent`, `branchPoint`, `edits`, `seed` and `hash`; a branch's hash covers its parent's hash, branch point and edits (`branchHash`), and a root's covers the engine, seed and model, code included (`rootHash`). `keepInModel()` returns the property edits as `node.setProps` commands, one per component, for the facade to dispatch as one undoable change, with the edits the model has no place for (state, code, structure) as `notKept`; `discard()` drops them. Either way `control.edits`, the run-only edits, empties. A run itself logs edits with their moment, so a replay makes them again then (`run.applyEdit(edit)`), and `run.fork()` starts a run at the same moment that shares its snapshots and a copy of its trace. `run.components` lists its components, `run.stateOf(id)` copies one's state, and `run.hasWork(id)` says whether one has calls or messages on their way.
- `compareRuns(a, b, moment)` (`src/compare.js`): moves two runs to the same moment and returns their differences: metrics by component and name (count, sum and last value) and state, field by field.
- `planRun(core, { modes, behaviours, scope, stubs })` (`src/plan.js`): a run's nodes and edges from the model, for the whole project or a scope. Core's `planModel` plans them as plain data, which the page can do without simulation code, and `withBehaviours(plan, behaviourOf)` (`src/behaviours.js`) gives each component its behaviour and each stub the behaviour that answers for it (task 0417). Each component is named by its path of node ids from the root (`payments/ledger/ledgerApi`), with its manifest (a System's ports expose the methods bound on them), effective properties and the behaviour for its type id; each edge carries its method and effective properties. Each composite runs in its mode from `modes`, by path: by default a System runs expanded and a component opened as a system as a black box. Expanded, its inner system is planned too, with each binding resolved one level down through core's `resolveBinding(…, { levels: 1 })` and each out port's inner port through `resolvePort`; as a black box, nothing inside it is planned.
  - **Snapshots and time travel** (spec §12, eng §13, ADR 0023, task 0413). A run takes a snapshot before anything happens, at time zero after the `init` hooks, at the first quiet event boundary after every `snapshotEvery` events (10,000 by default), and when `runToEnd` pauses at a quiet moment. Quiet means no method is suspended at an `await`: a suspended method is a continuation no copy can capture. A snapshot is plain data: every component's state, servers and the calls waiting for them, the event queue with references turned into ids and indices, every random stream's position, the counts of the trace and outputs, and the spans still running. `run.snapshots` lists them, by event and time; when they hold more than `snapshotBytes` (256 MB by default), the one whose neighbours are closest goes, the oldest first, never one at time zero or the latest. `await run.seek({ event })` or `seek({ timeUs })` reaches that moment as a run from zero would: going back, it restores the latest snapshot before it and replays forward. `await run.step(n, unit, { trace, sliceMs })` steps n units forward, or back for a negative n: `event`, `hop` (a message arriving at any component), `followed` (a hop of one trace), `call` (a public or private call starting or finishing, all of one event's at once) or `time` (slices of `sliceMs`, 10 ms by default). A step in hops, followed hops or calls ends right after the event that makes it, so stepping forward n then back n comes back to the same moment. `run.position` is `{ event, timeUs }`, and `run.stateHash()` hashes everything a moment holds. Requests injected from outside are logged with how many events had run, so a replay schedules them at the same moment; one injected behind the furthest point reached starts a new future, dropping the later snapshots and injections.
  - **Observing and inspecting** (spec §13, task 0416). `run.observe(listener)` tells the listener what happens inside each event, until the function it returns is called: `{ type: 'call', kind, node, method, span }` when a public or private call starts, `{ type: 'arrive', node, port, method, message }` when a message arrives at a component, `{ type: 'depart', node, port, edge, method, message }` when one leaves over an edge, and `{ type: 'log', node, level, args }`. With `inspect: true`, `run.messages` keeps every message that arrived, with its event, time, trace, node, port, method, kind, path, headers, body, size, attempt and edge; seeks and forks keep it to the moment. `run.inputOf(id)` is a component's input, `run.propsOf(id)` its property values now, and `run.appliedEdits` the run-only edits made so far, with their moments.
  - **Advancing with limits.** `await run.advance({ untilUs, untilEvent, until, before })` handles events as `runToEnd` does, and also until `until()` holds after an event, or before an event that `before(event)` holds for, as a breakpoint does. It says why it stopped: `before`, `until`, `event`, `time` or `end`.
  - **Scopes** (spec §11 "Scope", eng §13, task 0412). `scope` limits what runs, and nothing outside it is planned: `{ kind: 'project' }`, the default; `{ kind: 'system', node }`, a composite and its system at any depth, which runs expanded and is entered through its boundary ports; or `{ kind: 'selection', nodes }`. `requestPath(spans)` (`src/scope.js`) gives the selection a first trace run touched: each component that handled a call, and the composites its requests passed through.
  - **Stubs** (`src/stubs.js`). Each edge leaving the scope ends in a stub, `stub:<edge id>`, with the port it reaches and its methods, configured by edge id in `stubs`. A fixed stub, `{ mode: 'fixed', latency, errorRate, errorCode, response }`, answers after a draw from its latency, fails at its error rate (`UNAVAILABLE` by default), and otherwise answers with its response; with no configuration it answers `null` at once. A recorded stub, `{ mode: 'recorded', calls }`, replays a recording run's `recordings[edgeId]`, matched by method and call order, each after as long as it took; a call with none left fails with `E_STUB_NO_RECORDING`. A black-box stub, `{ mode: 'blackbox' }`, plans the component outside as a black box, without its inner system or its edges, so its own calls downstream fail with `E_SIM_NO_EDGE`.
  - **Inbound traffic.** `planRun` returns the edges entering the scope as `inbound`. `replayInbound(run, inbound, recordings)` injects what a recording run saw on each into the component at its end, at its original time after the run's current time, and returns the replies.
- `createRunSessions({ behaviourOf, scheduler, wallMs, post })` (`src/sessions.js`, ADR 0025, task 0417): the runs a worker keeps between messages, by id, which the worker's session and the in-process host share. `run.start { input, durationMs, frameMs, speed }` takes a planned run with the requests it is given (`inject`) and answers with a view; `run.control { run, action, args }` makes one control (play, pause, stop, restart, runToEnd, step, seek, setSpeed, follow, stepInto, stepOut, edit, resume, replayFromHere, restartWithChanges, keepInModel, discard, setBreakpoint, clearBreakpoints) and answers with the view of the moment it left the run at; `run.read { run, what }` reads its view, spans, metrics, logs, changes, hash, run tree or a comparison with another run, in `run.data` chunks of at most 64 KB; and `run.close` drops it and its branches (`E_RUN_NOT_FOUND` after). Each run in a control's tree has its own id, such as `s1.run-2`; only the current one moves, and one that went on as a branch or was restarted keeps the moment it was left at (`E_RUN_STATE` for a control). Stepping, seeking and running to the end play and pause a ready run first, and pause a playing one, in one task, so no frame plays between; followed hops follow the first request when none is followed. A view is plain data: the run's id, status, position, speed, followed trace and frame, run tree, run-only edits and ways to continue, every component's state and the metric totals. A long action posts a heartbeat every 250 ms of wall time, and a playing run posts its view at most every 100 ms of wall time and when it stops. Messages are handled one at a time, in order.
- `workerAdapters(scope)` (`src/worker/bootstrap.js`): the worker's scheduler, on its own timers, and its wall clock, taken before the sandbox makes `performance.now` simulated time; only the run sessions hold them.
- `runComponent({ manifest, behaviour, props, state, fixtures, seed, replies, edges })` (`src/component.js`, ADR 0020): one component in the kernel, for self-tests that need simulated time, servers or timers. Properties are written as people write them (`'5s'`). Each out port reaches a stub that answers from `replies`, by `'port.method'`, or by `'port'` for a send that names no method; a reply that throws answers with a failure of its `code`. `edges`, by port, gives the edge to its stub connection properties, such as `{ out: { latency: 80 } }`, so a test can make an upstream slow. `targets`, by port, puts one stub per name behind it, such as `{ out: ['a', 'b'] }`; each answers by `'a.method'` or `'a'` before the port's replies, a reply function gets `{ node }` after the body, and `edges['out:a']` sets that edge alone. `call(method, body, { port, atMs, path, headers, sizeBytes })` sends a request and returns its reply, and `await runUntil(ms)` handles the events due by then; `spans`, `metrics` and `changes` are the run's.
- `createTestContext(options)` (`src/testing.js`, task 0303): a `ctx` for unit tests, with no kernel. Props start from the manifest's defaults, and state from its initial values. `ctx.call` runs the behaviour's private methods, and `ctx.send` answers from `replies`, by `'port.method'`, or by `'port'` for a send that names no method (ADR 0019). It records what a method sends and emits (with their protocol details), calls, fails, measures, logs, schedules and spends, as plain copies, and every state change with its path. `ctx.now` is a plain property, which `spend` moves on. `ctx.targets` answers from its `targets` option, by port. Setting a state field the manifest does not declare throws. It moved here from strata-plugins (ADR 0017's amendment).
- Both are Node-only helpers, which `strata/testing` exports and the worker never imports.
- `sample(dist, u)` and `probit(p)` (`src/sample.js`): distribution samples from a uniform number, with sim's `log` and `exp`, so they are the same in every engine.
- `simulate(input)`: one request from a client to a service over one edge, with fixed latencies. It returns the trace, the response and the run hash (`runHash`, SHA-256 from core).
- `handleMessage(message)`: the worker protocol, `{ v, type, id, payload }`, for `run`.
- `src/worker/main.js`: the worker entry. `npm run build` bundles it into `dist/sim-worker.js`, which a `file://` page starts from a Blob URL. Node runs the same bundle in `worker_threads` (strata-server's `spawnThreadWorker`).
- `src/worker/bootstrap.js`: the sandbox (spec §8). Before any component loads it removes `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `indexedDB` and `caches`, and `Worker` and `SharedWorker`, whose own globals would reach them. It deletes each from the prototypes that provide it too. `Math.random` becomes the seeded stream of the component that runs, and `Date.now` and `performance.now` return simulated time in ms. Component behaviours arrive as script text (strata-plugins' `behaviourScript`) and load through a Blob URL with `importScripts`, which the strict CSP allows. WebKit refuses that Blob URL from a `file://` page, where no CSP applies, so there the bootstrap evaluates the same text with an indirect eval (eng §16). After that it removes `importScripts`, before any behaviour module runs. It is the one file allowed to evaluate code (eng §16).
- `createWorkerSession({ post, sandbox, scheduler, wallMs })` (`src/worker/session.js`): what the worker does with each message. `load` evaluates behaviour scripts, once per worker. `call` runs one public method of a loaded component at a simulated time with a seed, as a unit-style injection (spec §11); it posts a heartbeat naming the method before it starts. Replies move the buffers of their typed arrays as Transferables.
- The page's side of the worker, `createSimHost({ spawn, scheduler })`, is in the facade (`packages/facade/src/sim-host.js`), so the main thread carries no simulation code; strata-sim ships only in the worker bundle (ADR 0018). It starts a worker with the `spawn` it is given, pairs each reply with its request by `id`, and refuses a worker that speaks another protocol version. Its watchdog, on the injected scheduler, stops a worker that stays silent for 2 s while requests wait, and rejects them with `E_SIM_METHOD_HUNG`, naming the method the last heartbeat said had started. The next request starts a fresh worker. The app's host (`app/sim-host.js`) spawns Blob-URL Web Workers.
- `createInProcessSimHost({ behaviours, scheduler, wallMs })` (`src/protocol.js`): a host that answers the worker's messages in the calling thread, run sessions included, copying each message both ways as posting does, for Node scripts and tests (`createStrata({ simHost: createInProcessSimHost({ behaviours, scheduler }) })`). It has no sandbox or watchdog and evaluates no code: `load` loads nothing, and runs take their behaviours from `behaviours`, by `id@version` or id. `listen(listener)` hears the views of playing runs. `inProcessSimHost` is one with no behaviours or scheduler, for the walking skeleton and base behaviours.
- `PROTOCOL_VERSION` is core's `SIM_PROTOCOL_VERSION`, which the facade's host reads too.

The worker names a hung method only for a `call`, which says which method it starts. Inside a long run action it posts `heartbeat { run }` every 250 ms of wall time, so the watchdog stops only a worker that has really gone silent; naming the method that hangs inside a run is left for later.
